# W3.3 — Email availability delivery

## Decision

Use a provider-agnostic outbox in Supabase and keep provider credentials server-side.

Initial provider path: **Brevo transactional email API**, because the current official mailbox is `mtgdisplaycr@gmail.com` and Brevo supports verification of an individual sender address. A custom authenticated domain remains the recommended production upgrade for deliverability and brand alignment.

Do not couple Wishlist matching directly to a provider API. Matching creates an availability event; eligible email delivery creates an outbox job; a server-side worker sends it.

## Sender

- Display name: `MTG Display CR`
- Initial sender mailbox: `mtgdisplaycr@gmail.com`
- Reply-to: `mtgdisplaycr@gmail.com`
- Future preferred sender after a domain is available: e.g. `notifications@<owned-domain>`

The Gmail address must be verified with the selected provider before real sending is enabled.

## Flow

1. Inventory publish/update creates the existing Wishlist availability event.
2. Resolve the Wishlist owner.
3. Read `notification_preferences.email_enabled`.
4. If email is disabled, do not enqueue an email.
5. Resolve the user's authenticated account email.
6. Insert one `email_notification_outbox` row using the availability notification/event as the dedupe key.
7. A server-side worker claims pending rows.
8. Render `wishlist_available` in the user's ES/EN locale.
9. Send through the configured provider.
10. Persist provider message ID and mark `sent`, or persist a safe error and retry metadata.

## Template contract: `wishlist_available`

Payload should contain only the data required to render the message:

- card name
- set name/code
- collector number
- requested finish
- requested language
- requested condition
- compatible-offers URL

The email must lead to Compatible Offers. It must not automatically select or promote a seller.

Suggested subject:

- ES: `Una carta de tu Wishlist ya está disponible`
- EN: `A card from your Wishlist is now available`

## Retry baseline

- `pending` -> `processing` -> `sent`
- transient failure -> `failed` with `attempt_count + 1` and `next_attempt_at`
- cap automatic attempts at 3 for the first implementation
- do not retry permanent recipient/provider validation failures automatically
- dedupe by user + availability notification/event + template

## Security

- Never expose the provider API key to browser/client code.
- Store the provider key as a Supabase Edge Function secret or equivalent server-side secret.
- Do not commit `.env` values.
- The outbox has RLS enabled and intentionally has no client policies.
- Do not place provider secrets in the outbox payload.
- Keep delivery errors sanitized; avoid storing unnecessary message content or personal data.

`EMAIL_FROM_NAME=MTG Display CR`
`EMAIL_FROM_ADDRESS=mtgdisplaycr@gmail.com`
`EMAIL_REPLY_TO=mtgdisplaycr@gmail.com`

## Activation gate

Real email sending remains OFF until all are true:

- sender verified in provider
- API key configured server-side
- W3.2 `email_enabled` preference verified in production
- enqueue integration tested
- template reviewed in ES and EN
- failure/retry path tested

## Custom-domain upgrade

Before meaningful production volume, move to an owned sending domain and configure SPF/DKIM/DMARC according to the provider's instructions. Free mailbox domains such as Gmail cannot be DNS-authenticated by this project because MTG Display CR does not control `gmail.com`.
